# اختبار فصل القراءة والكتابة باستخدام k6

يستخدم الاختبار [read-write-verification.js](./read-write-verification.js) للتحقق من إنشاء طلب ثم ظهوره مباشرة في قائمة طلبات الإدارة.

## قبل التشغيل

- شغّل خدمات المشروع، وتأكد أن `backend` و`mysql-primary` و`mysql-replica` تعمل.
- استخدم حساب إدارة صالحًا لديه صلاحية عرض جميع الطلبات.
- اختر `PRODUCT_ID` لمنتج موجود ومخزونه متاح في خدمة المخزون.
- شغّل الأوامر من PowerShell في مجلد المشروع.

## التشغيل

ضع بيانات الدخول ومعرّف المنتج في نافذة PowerShell الحالية، ثم شغّل حاوية k6:

```powershell
$env:TEST_EMAIL = "admin@example.test"
$env:TEST_PASSWORD = "<كلمة-مرور-حساب-الاختبار>"
$env:PRODUCT_ID = "1"

docker compose --profile load-test run --rm --no-deps `
  -e TEST_EMAIL -e TEST_PASSWORD -e PRODUCT_ID `
  k6
```

استبدل البريد وكلمة المرور ومعرّف المنتج بقيم صالحة في بيئتك. لا تحفظ كلمة المرور في ملف أو تشاركها. إذا ظهر `Set TEST_EMAIL and TEST_PASSWORD` فتأكد من تعيين المتغيرات في نافذة PowerShell نفسها التي تشغّل منها الأمر.

## خطوات الاختبار

1. يرسل السكربت بيانات الدخول إلى `POST /api/v1/users/sign-in` ويحصل على JWT.
2. يرسل `POST /api/v1/orders` لإنشاء طلب بكمية واحدة من المنتج المحدد.
3. يأخذ رقم الطلب من الاستجابة.
4. يرسل `GET /api/v1/orders/admin` مباشرة، ويتحقق من ظهور الطلب الجديد.
5. يعرض نتائج التحقق وقياسي زمن الكتابة والقراءة.

الافتراضي هو مستخدم افتراضي واحد وتكرار واحد. كل تكرار ناجح ينشئ طلبًا حقيقيًا ويستهلك وحدة من المخزون. لا ترفع الحمل إلا في بيئة اختبار وبمخزون كافٍ:

```powershell
$env:TEST_ITERATIONS = "5"
$env:TEST_VUS = "1"

docker compose --profile load-test run --rm --no-deps `
  -e TEST_EMAIL -e TEST_PASSWORD -e PRODUCT_ID -e TEST_ITERATIONS -e TEST_VUS `
  k6
```

## قراءة النتيجة

- `checks rate=100%`: نجحت فحوص إنشاء الطلب وظهوره في القراءة.
- `POST order is created successfully`: إنشاء الطلب أعاد HTTP 201.
- `immediate GET sees the new order`: ظهر الطلب في استجابة قائمة الإدارة.
- `order_write_duration` و`order_immediate_read_duration`: زمن استجابة العمليتين بالميلي ثانية.
- `http_req_failed`: نسبة طلبات HTTP التي فشلت.

إذا فشل تسجيل الدخول بـHTTP 422، فتحقق من وجود المستخدم والبريد وكلمة المرور في قاعدة البيانات الحالية. وإذا لم يظهر الطلب في القراءة، افحص صلاحية الإدارة واتصال الـReplica وتأخر النسخ.

## حدود التحقق

نجاح القراءة الفورية لا يثبت وحده أن GET خُدم من الـReplica أو أن POST نُفذ على الـPrimary؛ يلزم التحقق من المضيف عبر مراقبة اتصالات/استعلامات قاعدة البيانات. كذلك، `sticky => true` يضمن توجيه القراءة إلى اتصال الكتابة بعد كتابة ضمن **طلب Laravel نفسه**، وليس تلقائيًا بين طلبَي HTTP منفصلين (POST ثم GET). لذلك هذا السكربت يتحقق من ظهور الطلب فعليًا بعد الإنشاء، لكنه لا يثبت أن `sticky` هو سبب الاتساق.
